## Задача 1: API Gateway

Для реализации API Gateway рассмотрим следующие решения:

- Kong Gateway  
- Traefik Proxy  
- NGINX  
- Spring Cloud Gateway  

### Сравнительная таблица

| Решение | Маршрутизация запросов | Аутентификация | HTTPS termination | Плюсы | Минусы |
|--------|----------------------|---------------|------------------|------|-------|
| **Kong Gateway** | Да | Да (JWT, OAuth2, OIDC, Key Auth) | Да | Готовый API Gateway, плагины, гибкость | Часть функций в enterprise |
| **Traefik** | Да | Частично (через middleware) | Да | Простота, интеграция с Kubernetes | Ограниченные возможности API management |
| **NGINX** | Да | Частично (JWT в Plus версии) | Да | Высокая производительность, распространенность | Требует ручной настройки |
| **Spring Cloud Gateway** | Да | Да (через Spring Security) | Да | Отлично для Spring-экосистемы | Привязан к Java |

---

### Выбор решения

**Я бы выбрал Kong Gateway**

### Обоснование

Kong является полноценным API Gateway и из коробки поддерживает:

- маршрутизацию запросов;
- проверку аутентификации (JWT, OAuth2, OpenID Connect, Keycloak);
- HTTPS termination;
- расширение через плагины (rate limiting, ACL, логирование и др.).

Почему не другие решения:
- Traefik проще, но менее функционален;
- NGINX требует ручной сборки логики API Gateway;
- Spring Cloud Gateway ограничен Java-экосистемой.

## Задача 2: Брокер сообщений

Рассмотрены следующие брокеры:

- RabbitMQ  
- Apache Kafka  
- NATS JetStream  
- Apache Pulsar  

---

### Сравнительная таблица

| Решение | Кластеризация | Хранение на диске | Скорость | Форматы сообщений | Разграничение доступа | Простота эксплуатации | Особенности |
|--------|--------------|------------------|----------|-------------------|----------------------|----------------------|-------------|
| **RabbitMQ** | Да | Да | Высокая | Любые (JSON, XML, binary) | Да | Простая | Классические очереди |
| **Kafka** | Да | Да | Очень высокая | Любые | Да | Сложная | Стриминг данных |
| **NATS JetStream** | Да | Да | Очень высокая | Любые | Да | Очень простая | Лёгкий и быстрый |
| **Pulsar** | Да | Да | Очень высокая | Любые | Да | Сложная | Мощная архитектура |

---

### Выбор решения

**Я бы выбрал RabbitMQ**

---

### Обоснование

RabbitMQ соответствует всем требованиям:

- Поддерживает кластеры и отказоустойчивость.
- Поддержка durable очередей, persistent сообщений, quorum queues.
- Достаточно высокая производительность для большинства микросервисных сценариев.
- Поддерживает любые форматы: JSON, XML, Protobuf, бинарные данные.
- Гибкое разграничение доступа через: пользователей, virtual hosts, permissions.
- Простота в эксплуатации: удобный web UI, понятная конфигурация, хорошая документация.

---

Почему не другие решения:
- Kafka сложнее в эксплуатации, избыточен для обычных очередей, больше подходит для стриминга.
- Pulsar тяжелее в сопровождении, сложная архитектура (Broker + BookKeeper).
- NATS JetStream очень быстрый и простой, но менее распространён и менее универсален в enterprise.
