# Домашнее задание к занятию «Микросервисы: подходы»


## Задача 1. Обеспечить разработку

Для организации процесса разработки я предлагаю использовать **GitLab Cloud (GitLab.com)** как основную платформу и **GitLab Runner** на собственных серверах компании как исполнитель сборок.

Такое решение хорошо подходит для микросервисной архитектуры, потому что каждый сервис можно хранить в отдельном Git-репозитории, а процессы сборки, тестирования и поставки описывать рядом с кодом в файле `.gitlab-ci.yml`. В итоге разработчики работают в одной системе: там лежит код, там же запускаются пайплайны, там же видны результаты сборки и доставки.

### Как это будет работать

Каждый микросервис хранится в отдельном репозитории GitLab. Когда разработчик делает commit, push или открывает merge request, GitLab автоматически запускает pipeline. Кроме автоматического запуска, pipeline можно запускать вручную из интерфейса и передавать в него переменные: например, имя окружения, версию образа, флаг включения тестов или адрес стенда.

Сами сборки выполняют GitLab Runner, которые разворачиваются на наших серверах. Это удобно: управляющая часть остаётся в облаке, а вычисления, сборка Docker-образов и доступ к внутренним ресурсам компании происходят внутри нашей инфраструктуры.

Обычно схема будет такой:

**GitLab Repository → GitLab CI/CD Pipeline → GitLab Runner → Container Registry / среда развертывания**

Секреты, такие как пароли, токены и ключи доступа, хранятся в защищённых переменных GitLab. Для более строгих требований безопасности можно дополнительно подключить HashiCorp Vault.

### Обоснование выбора решения

GitLab является облачной системой и работает с Git-репозиториями. Для каждого сервиса легко создать отдельный проект. Сборки могут запускаться по событиям из системы контроля версий, а также вручную по кнопке с передачей параметров.

Настройки можно привязывать как ко всему проекту, так и к отдельным job и pipeline. В GitLab есть шаблоны `.gitlab-ci.yml`, include-файлы и переиспользуемые блоки, поэтому удобно делать типовые шаблоны для Java-сервисов, Python-сервисов, frontend-проектов и так далее.

Из одного репозитория можно запускать несколько разных конфигураций сборки: например, отдельно lint, unit-тесты, сборку Docker-образа и деплой в dev. Для этого достаточно описать разные job или разные pipeline-ветки с условиями запуска.

Кастомные шаги поддерживаются без ограничений, потому что job по сути выполняет набор команд shell. Можно использовать собственные Docker-образы для среды сборки, например образ с Maven, Node.js, .NET SDK или любым внутренним инструментарием компании.

GitLab Runner можно установить на свои серверы, разбить по тегам и выделить отдельные группы раннеров под backend, frontend, security scan или production deployment. Параллельный запуск сборок и тестов поддерживается штатно: несколько job выполняются одновременно, а тесты можно разделять по стадиям или по матрице.

## Задача 2. Логи

Для централизованного сбора и анализа логов я предлагаю использовать связку **Vector + Kafka + OpenSearch + OpenSearch Dashboards**.

### Как это будет работать

На каждом хосте или в каждом контейнерном узле работает агент **Vector**. Он забирает логи из `stdout` контейнеров и системных журналов, добавляет служебные поля, например имя сервиса, хост, окружение и уровень логирования, и отправляет данные дальше.

Чтобы обеспечить надёжную доставку, логи сначала отправляются в **Kafka**. Она выступает как промежуточный буфер и защищает систему от потерь при временной недоступности центрального хранилища. Если OpenSearch недоступен или перегружен, сообщения не теряются, а продолжают храниться в Kafka до обработки.

Далее отдельный консьюмер или агрегатор читает данные из Kafka и записывает их в **OpenSearch**. Для поиска и анализа разработчики используют **OpenSearch Dashboards** через веб-интерфейс.

Схема получается такой:

**stdout приложений → Vector на хостах → Kafka → OpenSearch → OpenSearch Dashboards**

### Обоснование выбора решения

Логи собираются централизованно со всех хостов. От приложений не требуется сложная интеграция: достаточно писать логи в `stdout`, что очень удобно для микросервисов и контейнеров.

Требование по гарантированной доставке закрывается за счёт двух вещей. Во-первых, Vector умеет использовать буферы, в том числе дисковые. Во-вторых, Kafka надёжно хранит сообщения до тех пор, пока они не будут обработаны. Это намного надёжнее, чем отправлять логи напрямую в поисковый движок.

Для поиска и фильтрации по логам подходит OpenSearch. В нём можно искать по времени, сервису, уровню ошибки, trace-id, hostname и любым другим полям. OpenSearch Dashboards даёт удобный веб-интерфейс, где разработчики могут самостоятельно искать ошибки и анализировать события.

Доступ разработчикам можно выдавать по ролям. Например, одна команда видит только свои индексы или только логи определённого окружения. Также в интерфейсе можно сохранять поисковые запросы и передавать ссылку на сохранённый поиск коллегам.

В задании есть важное требование: **гарантированная доставка логов**. Именно поэтому я добавляю Kafka как промежуточный слой. Она делает архитектуру устойчивее и лучше подходит для большой компании, где объём логов может быть высоким, а центральное хранилище может периодически испытывать нагрузку.

Vector я выбираю как лёгкий и современный агент. Он хорошо подходит для работы с контейнерными логами, умеет преобразовывать записи и поддерживает буферизацию.

OpenSearch я выбираю как центральное хранилище, потому что он хорошо решает задачу быстрого поиска по логам, а OpenSearch Dashboards закрывает требование по пользовательскому интерфейсу и совместной работе с сохранёнными запросами.

## Задача 3. Мониторинг

Для мониторинга состояния хостов и сервисов я предлагаю использовать связку **Prometheus + Node Exporter + cAdvisor + Grafana**.

Если в системе есть Kubernetes, дополнительно можно использовать **kube-state-metrics**, но даже без него основная связка уже закрывает требования задачи.

### Как это будет работать

На каждом хосте устанавливается **Node Exporter**, который отдаёт метрики по CPU, RAM, дискам и сети. Для контейнеров и сервисов можно использовать **cAdvisor**, который показывает потребление ресурсов по каждому контейнеру: процессор, память, файловая система и сетевой трафик.

Сами сервисы, если нужно, отдают свои бизнес-метрики в формате Prometheus. Например, количество запросов, время ответа, число ошибок, длину очереди, количество активных сессий и так далее.

**Prometheus** регулярно опрашивает все эти источники и сохраняет метрики в своей базе. Затем **Grafana** подключается к Prometheus и показывает данные в виде графиков, таблиц и дашбордов.

Схема получается такой:

**Node Exporter / cAdvisor / метрики сервисов → Prometheus → Grafana**

### Обоснование выбора решения

Сбор метрик со всех хостов обеспечивается через Node Exporter. Метрики по CPU, RAM, HDD и Network он отдаёт из коробки. Метрики потребления ресурсов по сервисам и контейнерам обеспечивает cAdvisor.

Специфичные для сервиса метрики также легко собирать, потому что Prometheus поддерживает единый формат и огромное количество клиентских библиотек. Для Java, Go, Python, .NET и других платформ это стандартный и очень распространённый подход.

Для запросов и агрегации используется язык **PromQL**, а интерфейс Grafana позволяет удобно строить панели, фильтровать данные, сравнивать окружения и собирать общие дашборды по системе. Можно сделать отдельные панели для инфраструктуры, отдельные — для конкретного микросервиса, отдельные — для бизнес-метрик.

Grafana хорошо подходит для повседневной работы, потому что в ней удобно создавать наглядные панели: например, здоровье всех сервисов, загрузку нод, ошибки по API и задержки по базам данных.

Prometheus стал стандартом де-факто для мониторинга контейнерных и микросервисных систем. Он хорошо подходит именно для динамичной среды, где сервисов много, они часто обновляются и могут быстро появляться или исчезать.

Grafana даёт понятный и удобный интерфейс для команд разработки, эксплуатации и руководителей. При этом связка не перегружена лишними компонентами и довольно проста в сопровождении.

Node Exporter и cAdvisor решают инфраструктурную часть задачи, а сами сервисы могут постепенно отдавать дополнительные метрики без серьёзной переделки архитектуры.
