### 1
Минимальный набор метрик:
- Доступность HTTP-сервиса (HTTP status codes) — контроль работоспособности интерфейса взаимодействия с клиентами.
- Latency HTTP-запросов — оценка скорости отклика платформы.
- CPU utilization / load average — контроль ресурсов сервера вычислений.
- Disk usage (занятое место, I/O, inode usage) — контроль за свободным местом на диске, куда сохраняются отчеты.
- RAM usage — предотвращение OOM и деградации производительности.

### 2
Можно ввести бизнес-ориентированные показатели, понятные менеждеру продукта. Технические метрики CPU, RAM и т.д. оставить как вспомогательные для инженерной команды.
- SLA/SLO/SLI (доступность сервиса, доля успешных запросов, время ответа).
- Error rate (процент неуспешных запросов).
- «Процент успешно сформированных отчётов»
- «Доступность сервиса, %»

### 3
Без системы централизованных логов можно рассмотреть следующие варианты получения ошибок приложений:
- Настроить алерты по error-метрикам (HTTP 5xx, exceptions).
- Использовать stdout/stderr + системный журнал (journald, syslog) с локальной ротацией.
- Экспортировать ошибки в мониторинг через metrics endpoint.
- В качестве временной меры — уведомления в мессенджеры/почту из приложения или через алерты.
